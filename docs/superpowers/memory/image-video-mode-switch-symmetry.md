---
name: image-video-mode-switch-symmetry
description: "Image and video transports must have symmetric mode-selection helpers — Flow's editor remembers last-used mode per account; without an explicit switch, submissions silently route to the wrong endpoint and the listener times out"
---

Rule: Image and video transports in `src/gflow_cli/api/transports/` MUST have **symmetric** mode-selection helpers. Both `UiAutomationTransport._switch_to_image_mode` (in `ui_automation.py`) and `VideoGenerationMixin._switch_to_video_mode` (in `ui_automation_video.py`) exist; both are called once per editor mount after `_dismiss_blocking_overlays` and before any settings configuration. Any future change to Flow's mode-switch UI updates BOTH selector cascades in the same commit. The shared `MODE_SWITCH_TRIGGER_SELECTORS` constant lives in `ui_automation_video.py` and is imported by `ui_automation.py` — single source of truth for the dropdown trigger button.

**Why:** Flow's editor remembers per-account "last used mode" (Image or Video). If code assumes the editor opens in one mode but the account was last in the other, submissions silently route to the wrong endpoint. For image generation: no `batchGenerateImages` response is observed and the listener times out after 3 minutes. 2026-05-23 a `gflow image t2i` on `ffroliva` generated a video because the editor was last in video mode from a prior session — the image transport had no equivalent of the video side's `_switch_to_video_mode`. The historical "first-attempt listener-miss flake" recorded in [[phase-b-followups]] item #1 ("listener observed no batchGenerateImages URL at all after prompt_submitted") was almost certainly the same bug under a different name. Closed by PR #40.

**How to apply:**
- Adding a new mode (e.g., a future image-to-image or video-edit submode)? Add a `_switch_to_<mode>` helper. Its tab-selector cascade puts `[role='menu'] [role='tab'][aria-controls*='<MODE>']` first (locale-stable, semantic-attribute match), then Portuguese / English `has-text` fallbacks, then icon-ligature `:has(i:text('<icon>'))` as last resort.
- Wire from both single-shot and batch paths: after `_enter_editor` + `_dismiss_blocking_overlays`, before `_configure_generation_settings`. In the batch path wrap in the same `orphaned_project_warning` try/except as overlay dismissal (so a mode-switch failure on a freshly-created project surfaces the `project_id` for user lookup).
- Updating Flow's UI selectors (Flow ships a new aria attribute, drops a class, etc.)? Update both transports in one commit. If you find yourself updating only one side, you have a regression-in-waiting. PR #124 followed this correctly — `_exit_agent_mode` was added atop BOTH `_switch_to_image_mode` and `_switch_to_video_mode` in the same commit (see [[flow-agent-composer-mode-panel-removal]]).
- Unit-test pattern: `_cascade_page(visible: set[str]) -> MagicMock` fake Page where `locator(sel).first.wait_for` succeeds only for selectors in `visible`. Three tests per helper: happy path (trigger + tab both visible), trigger missing (assert `RuntimeError` match `"mode-switch"`), target tab missing (assert match `"<Mode> tab"`). See `tests/api/transports/test_ui_automation_image_mode.py` (image) and `tests/api/transports/test_ui_automation_video.py::TestSwitchToVideoMode` (video) for the canonical pattern.
- Orchestration tests (`generate_images`, `generate_images_batch`, `generate_video`) that don't care about the mode switch should stub it via `monkeypatch.setattr(UiAutomationTransport, "_switch_to_image_mode", AsyncMock())` (or the video equivalent) — see the autouse fixtures in `test_ui_automation.py::TestGenerateImages` and `test_ui_automation_batch.py` for the per-file pattern.

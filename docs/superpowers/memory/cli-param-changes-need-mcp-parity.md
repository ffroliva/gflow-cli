---
name: cli-param-changes-need-mcp-parity
description: Adding a CLI option OR a whole new CLI leaf command requires an MCP parity decision (mirror the tool, or exempt it) + running tests/mcp
---

Any new option/argument on a user-facing Click command (`gflow image t2i`, `gflow video t2v`, …) **must** be mirrored into the corresponding MCP tool definition in `src/gflow_cli/mcp/tools.py`. This is **AGENTS.md §61** ("MCP & CLI Schema Symmetry") and is enforced by `tests/mcp/test_server.py`.

**Why:** the contract keeps MCP/agent callers in parity with CLI users. The MCP image/video tools are still unwired scaffolds (return `"pending"`) and track a *curated* param subset (they omit `--duration`, `--out`, `--transport`, …), so the parity test only asserts a chosen set — it will NOT automatically fail for every missed param. The convention is the authority, not just the test.

**How to apply:** a CLI param change touches TWO test dirs that scoped api/data/cli runs miss — ALWAYS include both `tests/mcp` AND `tests/features`:
- `tests/mcp` — the CLI↔MCP parity gate (add the param to the MCP tool signature + returned `params` dict + extend the parity assertion in test_server.py).
- `tests/features` — BDD `_fake_t2i`/`_run_*` stubs mirror the runtime signature with TYPED kwargs; a new `_run_t2i(..., original_prompt=...)` kwarg raises `TypeError` in the stub, hashed to `error_unhandled` (the real message is hidden) → opaque CI failures. Add the kwarg to every `_fake_*` stub. See [[bdd-stubs-mirror-runtime-signatures]].

During prompt-expansion (PR #209, `-e/--expand`) I scoped to api/data/cli and missed BOTH: the MCP parity gap was caught by code review; the 3 `tests/features` BDD `TypeError`s slipped to red CI (commit fix after first push). Safest: run the FULL suite (or at least add tests/mcp + tests/features) before pushing a CLI-param change. See [[feature-dod-full-e2e]].

**A whole NEW LEAF COMMAND needs a parity DECISION, not just new options (2026-07-23, #345).** A separate, broader gate — `tests/mcp/test_cli_parity.py::test_every_cli_leaf_has_an_mcp_decision` (added 2026-07-09 skills-audit) — walks EVERY CLI leaf and fails unless each is in `CLI_TO_MCP` (mapped to a registered FastMCP tool) OR `_MCP_EXEMPT` (with a reason string). Shipping a new subcommand (e.g. `data errors export`/`prune`) means adding each leaf to `_MCP_EXEMPT` in that file — mirror the sibling entries (`data prune` = "destructive local … CLI-only", `data list errors` = "local catalog maintenance — not yet ported"). GOTCHA: missing this fails `test (3.11/3.12/3.13)` AND cascades to a **SonarCloud** failure — the aborted pytest never writes `coverage.xml`, so Sonar reads new-code coverage as 0 → quality-gate FAILED. A red Sonar here is a downstream symptom of the test abort, not a real coverage gap; fix the test first. `grep mcp/ for the command name` is NOT sufficient (these commands are deliberately absent from mcp/) — you must add the EXEMPTION. A scoped `pytest tests/cli` run does not touch `tests/mcp`; run `tests/mcp` before pushing any new CLI leaf.

**Fixed-container pattern beats per-flag §61 sprawl (tools framework, 2026-06-28).** When a CLI option is *repeatable + open-ended* (e.g. `--tool name[:k=v]`, repeatable across t2i/i2i/batch/t2v/i2v/r2v/chain), do NOT mirror each future tool as its own MCP param. Mirror ONE fixed **container** param — `tools: list[dict] = []` (`[{name, options}]`) — on `gflow_generate_image`/`gflow_generate_video`. The §61 parity test then asserts only that the `tools` container exists on both surfaces, so it stays green as tools accrue (no new MCP param per tool, no parity-test churn). The container is validated + adapted to CLI specs via `tools/invocation.py::tool_specs_from_invocations` (pydantic `ToolInvocation`) so malformed agent input fails cleanly rather than as an uncaught `TypeError` once the daemon wires generation. Same principle for any "list of opaque options" CLI flag. See [[prompt-expansion-feature]].

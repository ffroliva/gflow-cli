# MCP 2026-07-28 Spec — Impact Analysis & Strategy

**Date:** 2026-08-01 · **Base:** `develop` @ `fbc8917` (v0.46.1)

> **Status: recommendations applied in the same PR.** This document was written
> as analysis first; the P0/P1/P2 work and the cacheable-list piece of P3 then
> landed alongside it. See [§6 Implementation status](#6-implementation-status)
> for what shipped, what was deliberately declined, and what is deferred with a
> reason. The analysis below is preserved as written so the reasoning that drove
> the change is auditable.

## Executive summary

The MCP 2026-07-28 specification is the largest breaking change since the protocol launched: it
removes the `initialize`/`initialized` handshake and the `Mcp-Session-Id` header, moving MCP from a
stateful bidirectional protocol to a stateless request/response model. The Python SDK shipped this
as **`mcp` 2.0.0**, which **deletes the `mcp.server.fastmcp` module** that our entire MCP layer is
built on.

**We have a live P0.** `pyproject.toml` declares `"mcp>=1.0.0"` with no upper bound. `uv.lock` pins
`1.28.1`, so CI and contributors are green — but **anyone running `pip install gflow-cli` or
`uv tool install gflow-cli` today resolves `mcp` 2.0.0 and the MCP server fails to import**:

```
ModuleNotFoundError: No module named 'mcp.server.fastmcp'
```

Reproduced against a clean resolve of this repo's dependency set (2026-08-01).

The good news: once the pin stops the bleeding, the actual migration is far cheaper than the spec's
severity suggests. The SDK absorbs the protocol change for us — `Server.run` is a thin wrapper over
`serve_dual_era_loop`, which serves **both** the legacy handshake era and the modern
per-request-envelope era, with the client's first request deciding which. We get 2026-07-28 support
on stdio without writing a line of protocol code. The migration is a rename plus a transport swap.

**Verdict: pin now, migrate deliberately, then harvest.** The spec's stateless core is not a threat
to us (we are a local-first, single-user tool), but three of its new features — Tasks, Multi
Round-Trip Requests, and cacheable list results — map unusually well onto problems this codebase
already has.

## 1. What the spec actually changed

Read in full from the [spec changelog](https://blog.modelcontextprotocol.io/posts/2026-07-28/) and
the [release-candidate post](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/).

| Change | Detail |
|---|---|
| **Stateless core** | `initialize`/`initialized` handshake and `Mcp-Session-Id` removed. Protocol version and client capabilities now travel in `_meta` on **every** request (`io.modelcontextprotocol/protocolVersion`). |
| **Server-minted handles** | Servers needing cross-call state pass explicit handles as ordinary tool arguments. No connection-scoped state. |
| **Multi Round-Trip Requests (MRTR)** | Servers return `InputRequiredResult` mid-operation (confirmation, missing param). Client retries the original request with `inputResponses` + `requestState`. Replaces holding an SSE stream open. |
| **Header-based routing** | `Mcp-Method` and `Mcp-Name` HTTP headers let gateways route without parsing the JSON body. |
| **Cacheable lists** | `tools/list`, `prompts/list`, `resources/list` results carry `ttlMs` and `cacheScope`. |
| **`resultType`** | Now a mandatory field on results. |
| **`subscriptions/listen`** | Consolidated endpoint replaces HTTP GET + subscribe/unsubscribe. |
| **Tasks → extension** | Moved out of core into the official extensions framework (SEP-2663). Stateless: `tools/call` returns a task handle; the **client** drives `tasks/get` / `tasks/cancel`. `tasks/list` was removed (unscopable without sessions). |
| **Deprecated** | Roots, Sampling, Logging (still functional, 12-month minimum removal window). **HTTP+SSE transport reclassified as deprecated.** OAuth Dynamic Client Registration → Client ID Metadata Documents. |
| **Auth hardening** | RFC 9207 issuer validation; `application_type` fixes localhost redirect rejection for CLI/desktop apps; client credentials bound to issuing AS. |
| **Error code** | Missing resource: `-32002` → standard `-32602`. |
| **Lifecycle policy** | Formal Active → Deprecated → Removed states, minimum 12 months between deprecation and removal. |

The spec now has two explicit **eras**, and the SDK names them:

```
handshake era: ('2024-11-05', '2025-03-26', '2025-06-18', '2025-11-25')
modern era:    ('2026-07-28',)
```

## 2. Where gflow-cli stands

### 2.1 Current MCP surface

| Component | File | Lines |
|---|---|---|
| Server core (FastMCP instance, stdio/SSE boot) | `src/gflow_cli/mcp/server.py` | 161 |
| Tools (11 registered) | `src/gflow_cli/mcp/tools.py` | 1471 |
| Resources (3) | `src/gflow_cli/mcp/resources.py` | 97 |
| Prompts (2) | `src/gflow_cli/mcp/prompts.py` | 85 |

Transports: **stdio** (`gflow mcp run`) and **HTTP+SSE** (`gflow serve`, endpoints `/sse` +
`/messages/`).

### 2.2 The dependency split (the P0)

| Environment | How deps resolve | `mcp` version | Max protocol | Status |
|---|---|---|---|---|
| **CI** (`uv sync --extra dev`) | honours `uv.lock` | 1.28.1 | 2025-11-25 | ✅ green |
| **Contributors** (`uv sync`) | honours `uv.lock` | 1.28.1 | 2025-11-25 | ✅ green |
| **End users** (`pip`/`uv tool install`) | resolves `mcp>=1.0.0` | **2.0.0** | 2026-07-28 | ❌ **ImportError** |

This is the classic green-CI/broken-users split: the lockfile masks an unbounded range. CI will
never catch it, because CI never resolves the range.

**Blast radius:** total for the MCP surface. `src/gflow_cli/mcp/server.py:17` does
`from mcp.server.fastmcp import FastMCP` at module import, so `gflow mcp run`, `gflow serve`, and
`gflow mcp setup` all fail immediately on a fresh install. The pure-CLI paths are unaffected —
`mcp` is only imported from the `gflow_cli.mcp` package — so the damage is contained to the MCP
entry points, but within them it is complete.

### 2.3 What the 2026-07-28 stateless model costs us

Almost nothing, and this is the genuinely reassuring part of the analysis:

- **No session state to unwind.** Our server holds no per-connection state. Cross-call continuity
  lives in SQLite (`gflow.db`) and the Chromium profile directory, keyed by `profile` — which is
  already an explicit tool argument on every tool. That is, by accident, exactly the
  "server-minted handle passed as an ordinary tool argument" pattern the spec now prescribes.
- **`ProfileLease` is a file lock, not a session.** Cross-process by construction; a stateless
  protocol does not perturb it.
- **We use no Roots, Sampling, or Logging.** All three deprecations are no-ops for us.
- **stdio is unaffected in practice.** The dual-era loop negotiates on the first request.

The one real casualty is **SSE**. `gflow serve` runs on the transport the spec has now formally
deprecated.

## 3. Migration cost — measured, not estimated

The 1.x → 2.0 SDK move looks alarming (`FastMCP` deleted) but the replacement is near-identical.
Verified against `mcp` 2.0.0:

| What | 1.28.1 | 2.0.0 | Migration |
|---|---|---|---|
| Server class | `mcp.server.fastmcp.FastMCP` | `mcp.server.MCPServer` | rename, 1 site |
| Version | private hack: `server._mcp_server.version = ...` | first-class `MCPServer(version=...)` kwarg | **removes** our hack |
| `@server.tool(name=, description=)` | ✔ | ✔ **identical signature** | none |
| `@server.resource(uri=, name=, description=)` | ✔ | ✔ identical (+ new `icons`, `security`) | none |
| `@server.prompt()` | ✔ | ✔ | none |
| Low-level handle | `server._mcp_server` | `server._lowlevel_server` | rename, 2 sites |
| `stdio_server(stdout=...)` | ✔ | ✔ **same signature** | none |
| `create_initialization_options()` | ✔ | ✔ | none |
| `_tool_manager._tools` etc. (used by our tests) | ✔ | ✔ **still present** | none |
| Streamable HTTP | — | `run_streamable_http_async(path='/mcp', stateless_http=...)` | new option |

Our stdout-isolation path — the subtle bit, where we capture the real stdout *before* redirecting
`sys.stdout` to stderr — survives verbatim. `stdio_server` still accepts `stdout=`, and
`_lowlevel_server.run(read, write, init_options)` still has the same shape.

**Realistic cost: a focused half-day for the SDK migration**, dominated by re-running
`tests/mcp/` (which pokes `_tool_manager._tools` and friends — all of which still exist) and
`tests/mcp/test_stdio_transport.py` (the subprocess-level test that would actually catch a
stream-routing regression). The transport swap for `gflow serve` is a separate, larger piece.

## 4. Recommendations

### P0 — Stop the bleeding (do this before anything else)

**Bound the `mcp` dependency.** In `pyproject.toml`:

```toml
"mcp>=1.28,<2",
```

One line. It makes fresh installs resolve to the SDK our code actually targets and turns a silent
runtime `ImportError` into a resolver-level constraint. This should ship as a patch release
(`v0.46.2`) — every user who installed since `mcp` 2.0.0 hit PyPI has a broken MCP surface today.

**Add a resolution-drift guard to CI.** The pin is a bandage; the real defect is that CI only ever
tests the locked resolution. Add a job that installs the project **without** the lockfile
(`uv pip install .` from the `pyproject` ranges) and does a smoke import of `gflow_cli.mcp.server`.
That job is what would have caught this on the day `mcp` 2.0.0 was published, and it generalizes to
every other unbounded dependency we carry (`fastapi`, `uvicorn`, `httpx`, `playwright` are all
unbounded too — `mcp` is the one that broke first, not the only one exposed).

### P1 — Migrate to `mcp` 2.0 / MCPServer

Once pinned, migrate deliberately rather than under pressure:

1. `FastMCP` → `MCPServer`, passing `version=` properly and deleting the
   `server._mcp_server.version` private-API workaround at `server.py:35`.
2. `server._mcp_server` → `server._lowlevel_server` (2 sites in `server.py`).
3. Bump the pin to `"mcp>=2,<3"`, refresh `uv.lock`.
4. Run `tests/mcp/` — expect it to pass largely untouched. Update the FastMCP naming in test
   docstrings and `tests/mcp/conftest.py`.
5. Verify dual-era negotiation end-to-end with `tests/mcp/test_stdio_transport.py`, which drives a
   real subprocess and is the only test that would catch an era-negotiation regression.

**Payoff:** gflow-cli speaks 2026-07-28 to modern clients and 2025-11-25 to older ones, from the
same binary, with the SDK doing the negotiation. Claude's rollout of the new spec lands on a server
that already supports it.

### P2 — Replace SSE with Streamable HTTP

`gflow serve` is on a deprecated transport. Move it to `run_streamable_http_async` serving `/mcp`.
Keep `/sse` alive through one deprecation cycle — the spec's own 12-month lifecycle policy is a
reasonable model to copy, and `mcp` 2.0 still ships `run_sse_async` and the `mcp.server.sse` module,
so dual-serving is cheap.

Note the `stateless_http=True` option. We should **not** enable it reflexively: our value is a warm
daemon holding a live Chromium profile, which is the opposite of serverless. Stateless HTTP buys us
nothing and would fight `ProfileLease`. Ship it as `False` and document why — this is a case where
the spec's headline feature is correctly declined.

### P3 — Harvest the new features (where they genuinely fit)

This is where the spec stops being a tax and starts paying us back. Three features map onto problems
already in this codebase:

**a) Tasks extension — the strongest fit by a wide margin.**

`_run_generation_task` (`tools.py:191`) enqueues a job, claims it, `await`s it to completion, and
returns. A Veo generation is a multi-minute operation held open inside a single `tools/call`. That
is precisely the shape the Tasks extension exists to fix: return a task handle immediately, let the
client poll `tasks/get` and drive `tasks/cancel`.

We are unusually well-positioned here because **the durable state already exists**. `generation_queue`
in SQLite, with `enqueue_task` / `claim_task` / `get_task` and a real status field, is already a task
store — we built it for the worker daemon. Exposing it as MCP Tasks is mostly an adapter over
`QueueRepository`, not new infrastructure. And because the spec's Tasks are stateless (handles, not
sessions), our `task_id` UUID is already the right primitive.

This also closes the gap flagged in `website/docs/MCP.md:178` — the `FlowWorker` queue manager built
"as internal foundation but not yet wired into `gflow serve`". Tasks is the protocol-level reason to
finish that wiring, and it turns a long-standing internal-only component into a user-visible feature.

The one removed piece to design around: `tasks/list` no longer exists in the spec. Our
`gflow_list_projects`-style enumeration would need to stay a regular tool rather than lean on the
Tasks extension for listing.

**b) Multi Round-Trip Requests — a real answer to the auth dead-end.**

Today, expired cookies produce a terminal error: *"Authentication required. Run 'gflow auth login' in
your local terminal."* The agent's operation dies and the user context-switches to a shell. MRTR lets
us return `InputRequiredResult` instead and resume the original request once the user acts. The same
mechanism fits confirmation-before-spend, which matters for a tool that burns metered Flow credits —
the rate limiter and `GFLOW_CLI_DAILY_BUDGET` currently fail *closed* with an error where a
confirmation round-trip would be the better UX.

Worth scoping carefully: MRTR needs `requestState` to be reconstructible, and our generation payloads
are large. Prototype behind the auth case first, where the state is small.

**c) Cacheable list results.** `gflow_list_tools` reads a static registry; `gflow://db/schema` is a
constant. Both are free `ttlMs` wins. Low value, near-zero cost — bundle into the P1 migration rather
than tracking separately.

### Explicitly out of scope

- **Auth hardening (RFC 9207, CIMD, DCR deprecation).** We do no OAuth. `GFLOW_DAEMON_TOKEN` is a
  static shared secret for non-loopback binds, untouched by this spec.
- **Header-based routing (`Mcp-Method`/`Mcp-Name`).** Gateway/load-balancer infrastructure. We are
  local-first, single-user, single-instance. No action.
- **`subscriptions/listen`.** We publish no change notifications.
- **MCP Apps (SEP-1865).** Sandboxed HTML surfaces from the server. Interesting long-term against
  Gflow Studio / the `website/` UI, but speculative — note and revisit.

## 5. Strategic read

The spec is optimized for a deployment model we deliberately do not have: serverless, edge, load-
balanced, multi-tenant. Almost none of the stateless core's *motivation* applies to a tool that
drives a local Chromium profile under one user's credentials.

But the migration is nearly free, because the SDK's dual-era loop absorbs the protocol break, and
because our architecture was already stateless-shaped: state in SQLite, keyed by an explicit
`profile` argument that every tool already takes. We back into compliance without redesigning
anything.

The asymmetry to exploit: **we should decline the parts built for scale-out (stateless HTTP, header
routing, CIMD) and take the parts built for long-running work (Tasks, MRTR).** Video generation is
minutes-long, credit-metered, and auth-fragile — the three properties the new extensions target.
Tasks in particular is the rare case where a spec change hands us a protocol-blessed reason to finish
infrastructure we already built and shelved.

**Immediate action is the pin.** Everything else is planned work; that one is a live bug.

`mcp>=1.28,<2` was scoped as a stopgap to buy time for P1. Doing both at once
makes the stopgap moot, so the pin went straight to `mcp>=2.0.0,<3` and the
migration landed with it. The *durable* half of P0 — the CI job that would have
caught this on the day `mcp` 2.0.0 was published — still lands, and is the more
important of the two.

### One thing the migration surfaced that the analysis missed

`src/gflow_cli/ui/app.py` also consumed the SDK, via `server.sse_app(mount_path="/mcp")`.
mcp 2.0 dropped `mount_path`, and the replacement is not a rename: in 1.x that
shim split two values apart — the handshake **advertised** `/mcp/messages/` while
the POST route stayed mounted at `/messages/` inside the sub-app. mcp 2.0 derives
both from a single `message_path`, so they can no longer differ, but the sub-app
is mounted under `/mcp` (Starlette strips that prefix before dispatching inward),
which means they *must*.

Resolved by keeping the SDK default for the inner route — which also keeps the
SDK's auto-enabled DNS-rebinding protection, rather than hand-rolling the app and
silently dropping it — and adding an explicit `/messages/` alias for the path the
handshake advertises, in the same idiom the file already uses for `/mcp/message`.

This failure mode is silent (the stream opens; only the follow-up POSTs 404), so
it is pinned by `test_sse_message_endpoint_is_reachable_where_it_is_advertised`,
which reads the advertised endpoint off the transport and asserts the outer app
actually routes it. Worth recording that the MCP test suite did **not** catch
this — the full suite did.

### Why Tasks and MRTR are not in this PR

Both were assessed against the installed SDK, not deferred on vibes:

**The SDK ships no server-side Tasks implementation.** `mcp.types` has the wire
types (`CreateTaskResult`, `GetTaskRequest`, `TaskStatus`, …) and
`mcp.server.extension` has the generic `Extension` framework, but there is no
Tasks extension to enable and `tasks/*` is absent from `SPEC_CLIENT_METHODS`.
Adopting Tasks therefore means hand-rolling the `tasks/get` / `tasks/cancel`
handlers as a custom `Extension` subclass — new protocol surface area, not a
migration. The argument for doing it stands unchanged (see §4 P3a: our
`generation_queue` is already a stateless, handle-keyed task store, and `tools.py`
still blocks for minutes inside one `tools/call`), and the case is strong enough
to be worth its own plan. Landing it inside an SDK-migration PR would put new
protocol code on the credit-spending generation path — the most expensive and
least testable code in the repo — in a change that could no longer be reviewed
as a migration.

**MRTR has the same shape plus a client-support question.** `InputRequiredResult`
and `InputResponses` exist as types; what does not exist is a decision about how
`requestState` reconstitutes a generation request, and confirmation that the
clients we care about actually drive the retry. The auth dead-end remains the
right first prototype precisely because its state is small.

Recommended follow-up: `/gflow:plan mcp-tasks-extension`, gated on
`/gflow:predict` — this is exactly the "new transport / protocol surface" class
of change that gate exists for.

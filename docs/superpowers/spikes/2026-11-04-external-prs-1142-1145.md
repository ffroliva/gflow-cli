## Question

Each PR rests on a claim about Flow that its fake pages cannot test. Does each hold?

## #1143: Enter and Escape in the `@` picker

Every submit was aborted in the browser. A click on the real submit button recorded `ogiZ0b`, so the probe can see a submit. In the video arms no control click was sent, and `YhhmEf` was recorded from Enter alone.

| Gesture | Image | Video |
|---|---|---|
| Enter, no picker open | submit recorded, 4/4 | submit recorded, 2/2 |
| Idle 30 s after an aborted submit | nothing | not run |
| Enter on an open picker with 0 options | no submit, picker stays open | same |
| Escape on a miss | picker closed, `@` gone | same |
| `develop`'s Backspace cleanup | `@` left, picker open with 15 options | same |
| Retry with a real name after Backspace | 0 options | 0 options |
| Retry with a real name after Escape | 1 option | 1 option |

One earlier arm, run last in a sequence, recorded no submit for plain Enter in either mode. So plain Enter submits usually, not always. The cause was not found.

This reconciles the [2026-10-01 spike](2026-10-01-batch-ref-dropped.md): it tested an open, empty picker, and that still does not submit. The danger is Enter with no picker open.

A/B on `_mention_by_name`, a chip attached and then a miss:

| | `develop` | PR #1143 |
|---|---|---|
| Result | raw `TimeoutError` | `ReferenceNotFoundError` |
| Composer | stray `@`, picker open | clean |

`tests/e2e/test_mention_chip_order_bdd.py` passed on the PR's tree. It does not drive a miss.

The docstring's "measured 2026-10-13" has no support in that spike. This page is the measurement.

`_mention_character` retries with the same Backspace cleanup. That gesture was measured here on `_mention_by_name`; the character path itself was not run.

No false positive. A refusal that reaches the probe adds about 30 s. `tests/e2e/test_workspace_oracle_e2e.py` passed on `ffroliva`.

The PR can return `AUTHENTICATED` with `user_email=None`. `auth/real_chrome.py:500` asserts the email is non-empty, before it writes `.gflow_account`. Read in the code; `auth login` was not run on that path.

Not measured: a session revoked on the server with its cookies still on disk. These profiles refused, but nothing shows their sessions were revoked.

## #1142: reload past the agent-only composer

Forcing only the first verdict to `agent_only` on a real classic page: 1 reload, second verdict classic, and `run_images` went on through upload, settings and prompt to the submit.

That proves the loop, not the fix. The CLI and MCP send a new local `--ref` through `generate_reusing_uploads`, and `ui_automation.py:3025` refuses `agent_only` there. `_upload` does not catch that refusal, so `run_images` and its loop never run. This was read in the code and bypassed by the spike, which called `run_images` directly.

The probe's route did not record that submit, and the run ended with a lost-reply error, so one image may have generated. It was not confirmed either way.

Not measured: whether a reload escapes real agent-only serving. No profile we hold is in that cohort ([2026-10-17 spike](2026-10-17-agent-only-cohort-profiles.md)), which is a named external blocker.

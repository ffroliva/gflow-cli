# Design — README + AGENTS.md + llms.txt refresh for v0.8.1

**Date:** 2026-05-23
**Branch target:** `hotfix/readme-v0.8.1-refresh` off `main`
**Release:** signed tag `v0.8.1` → PyPI (trusted publish) → back-merge to `develop`
**Author:** Flavio Oliva (with Claude Code)

## 1 · Problem statement

`pyproject.toml` ships v0.8.0 but `README.md` still references v0.7.0 everywhere — Project status, "What's new", milestone table, install hints. The README has also grown to 398 lines (already at the project's own "keep under 400" governance limit in `docs/INDEX.md`) and lacks:

- A clearly-labeled **60-second quick start** vs an **in-depth** walkthrough.
- A **For AI agents & LLMs** section that routes coding agents (Cursor, Codex, Aider, Gemini CLI, Claude Code, …) to the right repo entry points.
- An honest, prominent statement of the project's **headed-browser dependency** — the single biggest barrier to scaling and the main place external contributors could help.

Worse, PyPI renders the README from the wheel that was uploaded for v0.8.0, so the package page on https://pypi.org/project/gflow-cli/ is locked at v0.7.0 content until a new tag publishes. A docs-only patch release is the only mechanism that refreshes it.

This spec defines the deliverable for that release.

## 2 · Goals

1. **Truth on PyPI** — the v0.8.1 wheel ships a README that reflects what 0.8.x actually does.
2. **Polished for humans** — first-time visitors can install, authenticate, and produce their first image or video in under 60 seconds of reading + ~2 minutes of command time.
3. **Routing for AI agents** — any LLM-driven coding agent that lands in the repo discovers `AGENTS.md` (universal spec) and is routed from there to `CLAUDE.md`, `docs/AGENT_GUIDE.md`, `docs/INDEX.md`.
4. **Honest about the constraint** — the headed-browser/Playwright dependency is documented as architectural reality AND as a contributor opportunity ("help us reach a full-REST transport"). Not a footnote.
5. **Documentation governance preserved** — README stays under 200 lines (was 398). Deeper material lives in `docs/`; `docs/INDEX.md` is the master TOC.

### Non-goals

- No changes to `src/gflow_cli/` runtime code. This is a documentation patch release only.
- No new docs site (mkdocs/Sphinx). `llms.txt` is forward-staged for that initiative but the site itself stays out of scope.
- No restoration of `gflow video i2v` / `gflow video batch` — that remains active Phase B work on `develop`.

## 3 · Architectural reality to surface

`gflow-cli` drives Google Flow today through a **headed Playwright Chromium session** (`ui_automation` transport). The HTTP transport is captured at the network layer for image generation but blocked for video by HTTP 401 + reCAPTCHA mints that Google's anti-bot stack enforces against headless / non-Chrome browsers.

This is the project's **defining trade-off**:

- ✅ It works today on a live Pro/Ultra account, end-to-end, with verified evidence.
- ❌ It requires a saved Chrome profile, a desktop display server (for the one-time login), and disk space for Playwright Chromium (~150 MB).
- ❌ It cannot run on a serverless/headless CI worker without prerecorded profile transplant.
- ❌ It cannot scale per-account beyond what one warm browser session can drive.

The README + AGENTS.md must state this **prominently and positively** — turning the caveat into a clear contributor signal: *"if you can unblock the all-REST path, you 10× the project's reach."*

```markdown
# gflow-cli

> Unofficial Python CLI for Google Flow — drive Veo (video) and Imagen (image) generations from your terminal.

[![PyPI](…)] [![CI](…)] [![Python](…)] [![License: MIT](…)] [![Status: alpha](…)]

> 🌐 **Headed-browser today.** gflow drives Flow via a persistent Playwright Chromium profile. Google's auth + reCAPTCHA gates currently require it. See [Architecture](#architecture--current-limitations) for the contributor opportunity.

## Why gflow-cli?

For Google AI Ultra / Pro subscribers with Veo credits and batch workloads:

- **Burn credits efficiently** — `for img in ./inputs/*.png; do gflow video i2v "$img" "$prompt"; done`
- **Build pipelines** — wire Veo into your content automation, AI video stack, or batch experiments
- **Stay in the terminal** — no Chromium UI, no clicking through dialogs (after a one-time `gflow auth login`)

Same Veo + Imagen models, same quality, same Ultra/Pro billing — programmatic.

## 60-second quick start

```bash
# 1 · Install
uv tool install gflow-cli
uv tool run --from gflow-cli playwright install chromium     # one-time, ~150 MB

# 2 · Authenticate (one-time, opens a real Chrome window)
gflow auth login --browser chrome

# 3 · Generate
gflow image t2i "a hot air balloon over Tokyo at sunrise"
# or:
gflow video t2v "Slow cinematic push-in on a sunlit forest clearing" --aspect 16:9
```

Outputs land under `./out/` (or `$GFLOW_CLI_OUTPUT_DIR`). First call is ~30-90s while Chromium warms; subsequent calls reuse the warm session.

> **Why `--browser chrome`?** Google rejects Playwright's bundled Chromium. The CLI fails fast with a friendly error if you pick anything else.

## Architecture & current limitations

```
gflow CLI  →  Provider (interchangeable)  →  Flow (ui_automation) / Mock (tests) / [planned: Official Veo]
                                              ↓
                                              Playwright Chromium (headed login, headless after)
                                              ↓
                                              aisandbox-pa.googleapis.com  (Google's private Flow API)
```

**Current transport:** `ui_automation` — drives Flow via a persistent Playwright Chromium profile. Production-stable, end-to-end verified per release (see [LIVE_VERIFICATION_*.md](docs/)).

**What's blocked:** A pure HTTP transport for video generation. The video upload endpoint returns HTTP 401 under non-Chrome browsers + a reCAPTCHA mint that we can't reproduce headlessly. Three earlier HTTP strategies (`evaluate_fetch` / `bearer` / `sapisidhash`) ship in an `experimental/` subpackage for archaeology.

**How you can help:** If you've successfully driven `aisandbox-pa.googleapis.com` from outside a real Chrome session — or have insight into Google's anti-bot stack here — please open an issue. A working REST transport would unlock serverless deployments, true horizontal concurrency, and would-be 10× the project's reach.

Full architectural detail: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## 5 · AGENTS.md skeleton (new, repo root, ~80 lines)

Follows the agents.md canonical sections — no required fields, conventional headers.

```markdown
# AGENTS.md — gflow-cli

> Universal entry point for AI coding agents. Read this first; everything else routes from here.

## Project at a glance
- Unofficial Python CLI for Google Flow (Veo + Imagen) — reverse-engineered private API.
- Python 3.11+ · uv-managed · Playwright Chromium transport · pyright strict · ruff · pytest.
- Single-package modular monolith: `src/gflow_cli/{api,cli,auth,config,errors,observability,paths,profile_store}`.

## Dev environment tips
- `uv sync` then `uv run playwright install chromium`. No global Python install needed.
- Headed-browser dependency — see the README "Architecture & current limitations" section.
- `.env.template` documents every env var. Copy to `.env.local`; never commit it.
- Output goes to `./tmp/` (script artifacts) or `$GFLOW_CLI_OUTPUT_DIR` (CLI outputs).

## Testing instructions — The Impeccable Routine
Run these five gates in order before every commit:
```powershell
$env:PYTHONUTF8=1
uv run python scripts/ci/check_repo_hygiene.py
uv run ruff check src tests
uv run ruff format --check src tests
uv run pyright src
uv run python -m pytest -q --cov=gflow_cli
```
- Use `pytest -m "not live and not e2e"` locally; full suite OOMs on small dev machines (scope to changed dirs, trust CI for the full sweep).
- TDD is non-negotiable. Coverage floor: 80% overall.

## Code style
- Type hints everywhere; pyright strict on `src/gflow_cli`.
- Structured logging (`structlog`) only — never raw `print()` or `import logging` in `src/`.
- Errors as RFC 9457 Problem Details with stable per-class exit codes (3–7, 14, 15).

## PR instructions
- Branch naming: `feature/`, `bugfix/`, `hotfix/`, `chore/`, `docs/`, `test/`, `release/` — never `claude/` or unprefixed.
- `develop` is the integration branch; `main` is protected. Releases tag off `main` only.
- **Never add AI attribution to commit messages.** Co-Authored-By: trailers are fine if asked; auto-generated "🤖 Generated with Claude Code" footers are not.
- Run `/gflow:check` (or the Impeccable Routine above) before every commit.

## Where to look next
- Architecture & target shape → [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)
- Mandates & routing rules (mandatory) → [docs/AGENT_GUIDE.md](docs/AGENT_GUIDE.md)
- Full docs index → [docs/INDEX.md](docs/INDEX.md)
- Known issues (read before touching auth / reCAPTCHA) → [KNOWN_ISSUES.md](KNOWN_ISSUES.md)
- Active phase & backlog → [PLAN.md](PLAN.md) or run `/gflow:plan`

## Claude Code-specific notes
[CLAUDE.md](CLAUDE.md) carries the auto-load instructions Claude Code reads natively. It now points back here for the universal rules; only Claude-Code-specific session protocol stays in CLAUDE.md.
```

## 15 · Risks & mitigations

| Risk | Mitigation |
|---|---|
| External deep-links break (people linking to `#project-status` etc.) | Keep anchor names where possible; for moved content, leave a 1-line redirect note pointing to the new file. |
| `AGENTS.md` is ignored if a tool only reads `CLAUDE.md` | CLAUDE.md keeps its own auto-load block but explicitly cross-references AGENTS.md so a Claude Code session still picks up the universal rules. |
| `llms.txt` confuses readers expecting a website-level file | Top-line in `llms.txt` itself says "forward-staged for a docs site at github.io/gflow-cli/llms.txt; usable today by LLMs you paste context into." |
| Releasing a docs-only patch feels like version-number waste | This is the only way to refresh PyPI's README. The alternative (waiting for the next code release) leaves stale v0.7.0 content public for weeks. PEP 440 `0.8.0.post1` was considered and rejected as less discoverable. |
| Back-merge conflicts on develop | `release-back-merge-gap-recovery` memory has the recipe; conflicts on `pyproject.toml` / `__init__.py` / `CHANGELOG.md` are expected, resolve in favor of develop except for the v0.8.1 bumps. |

## 1. Problem

PR #35 already contains a working bugfix + feature for issue #14, but it is a *starting point*, not production-ready:

- Branch name `claude/plan-next-issue-Stegy` violates the project convention (`feature/`, `bugfix/`, `fix/`, `docs/`, `test/`, `chore/`).
- Single squashed commit is authored by `Claude <noreply@anthropic.com>`; the PR body has a "Generated by Claude Code" footer. CLAUDE.md requires human-only attribution.
- No end-to-end test exists for `gflow image batch` or for the `-n N` native count selector — only unit tests.
- `--same-project` ships with a hard-coded 3–7s random jitter whose rationale (anti-bot-detection) is **plausible but unverified**. The project's standard is to *verify systematically, not guess*.
- Docs (`docs/USAGE.md`, `CHANGELOG.md [Unreleased]`, `docs/INDEX.md`) are not updated.
- Sample manifests for users to copy-paste are missing from `test_assets/`.
- A small piece of dead-parameter noise (`seed` / `batch_id` shim in `_drive_image_generation`) was left behind by the refactor.

## 2. Goal

Land a **production-ready, complete, correct, e2e-tested** multi-image prompt feature on `develop` via a clean PR from `feature/multi-image-prompt`, with:

- the bugfix and the new subcommand functionally unchanged where they're already correct;
- the jitter question **resolved empirically**, not by guesswork;
- a parameterized live e2e in the existing `tests/e2e/` family;
- documentation updates and committed sample fixtures;
- a clean commit history attributed to the human user, with no AI-co-author tags.

   - Drop the dead `seed`/`batch_id` shim from `_drive_image_generation` (verified by grep that no transport reads them).

   - Unit tests for parsing + dispatcher + orchestrator branches (shared vs. isolated project, fail-fast).

3. `test(e2e): live image batch e2e parameterized by jitter + same-project`
   - `tests/e2e/test_image_batch_e2e.py`, gated by `GFLOW_E2E=1`.
   - Env-var matrix per §7.
   - References `test_assets/sample_batch.tsv` so the test is self-contained.

4. `docs: gflow image batch in USAGE, CHANGELOG, INDEX`
   - `docs/USAGE.md` section.
   - `CHANGELOG.md [Unreleased]` entries.
   - `docs/INDEX.md` row for `LIVE_VERIFICATION_image_batch.md` (file added in commit #5).

5. **Evidence-driven** — `docs: image batch jitter live verification` plus *either* `refactor(image): drop unconditional jitter from --same-project` *or* `docs(image): document anti-detection jitter rationale on --same-project`
   - `docs/LIVE_VERIFICATION_image_batch.md` capturing the matrix outcomes (timestamps, prompts, HTTP statuses, observed throttling).
   - Code change (or its absence) decided by the evidence. The commit message cites the evidence file as the justification.

Atomic-commit rationale (CLAUDE.md): each commit captures one logical change and can be reverted independently. Splitting the bugfix from the feature lets us hotfix the count selector to a release branch without dragging in the new subcommand.

## 6. Mechanism for re-authoring the PR #35 work

Two viable mechanisms:

- **Mechanism 6.A — tree-replay + staged commits** (preferred for the split).
  1. Identify the PR #35 commit (`e8f932a`).
  2. `git checkout feature/multi-image-prompt` (based on `origin/develop`).
  3. `git checkout e8f932a -- src/gflow_cli tests` then selectively stage by area:
     - Stage the `_drive_images_generation` refactor + relevant unit tests → commit #1.
     - Stage the `image_batch.py` additions, `cli_image.py` wiring, fixtures, remaining unit tests → commit #2.
  4. Each commit is authored by the human user automatically (no `--author` override needed because we are not cherry-picking).

- **Mechanism 6.B — cherry-pick + interactive rebase** (fallback if 6.A produces a messy split):
  1. `git cherry-pick e8f932a` then `git commit --amend --reset-author --no-edit` (drops the Claude author).
  2. `git rebase -i origin/develop` to split via `edit` + `git reset HEAD^` + staged-by-area commits.
  3. **Reject if it requires an interactive editor inside the agent loop** — CLAUDE.md forbids `git rebase -i`. So 6.A is the actual plan; 6.B is a backup only for a human pairing session.

We will go with **6.A**.

**Note on the version bump in PR #35's diff.** PR #35 contained a `pyproject.toml` bump from `0.6.0a6 → 0.7.0` and a CHANGELOG footer update. Both are already on `develop` via the v0.7.0 release (PR #33). Tree-replay from `e8f932a` onto current `develop` produces no diff for these hunks — they silently disappear, which is correct. We do **not** bump the version in this PR; the next release (whichever it is) will do that.

## 7. E2E test design

File: `tests/e2e/test_image_batch_e2e.py`

Patterns to mirror:
- Gating, profile resolution, skip-reason copy, and `pytest.mark.e2e` from `tests/e2e/test_video_t2v_e2e.py`.
- Env-var parameterization style from the same file (validated as the existing pattern via `e2e-tests-parameterize` memory).

Env vars:

| Variable | Default | Purpose |
|---|---|---|
| `GFLOW_E2E` | unset | Master gate. Test is skipped unless `=1`. |
| `GFLOW_E2E_PROFILE` | `ui_automation` | Chrome-strategy profile (per `real-browser-auth-mandatory` memory). Fails fast if not Chrome. |
| `GFLOW_E2E_MANIFEST` | `test_assets/sample_batch.tsv` | Manifest under test. |
| `GFLOW_E2E_SAME_PROJECT` | `0` | `1` enables `--same-project`. |
| `GFLOW_E2E_JITTER` | `1` | `0` patches the jitter sleep to a no-op for the run. |
| `GFLOW_E2E_OUT_DIR` | `tmp/e2e_image_batch_<timestamp>` | Per the `tmp/`-output rule in CLAUDE.md. |

Assertions:
- Exit code 0.
- Expected number of image files written under `GFLOW_E2E_OUT_DIR`.
- Each file is a non-empty PNG (magic-byte check).
- Listener event `batch_response_seen` fires `count(manifest rows)` times.

Sample manifests (committed):

`test_assets/sample_batch.tsv`
```
a small calico kitten sitting on a windowsill
a watercolor sunset over rolling hills	2	16:9
an isometric pixel-art bakery	1	1:1	nano2
```

`test_assets/sample_batch.json`
```json
[
  {"text": "a small calico kitten sitting on a windowsill"},
  {"text": "a watercolor sunset over rolling hills", "count": 2, "aspect_ratio": "16:9"},
  {"text": "an isometric pixel-art bakery", "count": 1, "aspect_ratio": "1:1", "model": "nano2"}
]
```

These fixtures are intentionally short, safe-for-work, and exercise:
- default-everything row,
- explicit `count` + `aspect_ratio`,
- all four columns (TSV) / all four keys (JSON) including `model`.

## 8. Jitter investigation — the systematic part

**Question:** Is the 3–7s random delay between submissions inside `--same-project` necessary to avoid Flow rate-limits / anti-bot throttling, or is it cargo-cult?

**Method:** matrix run of the live e2e with three configurations against the 3-prompt sample TSV (jitter is only meaningful when same-project is on):

| Run | `SAME_PROJECT` | `JITTER` | Hypothesis if it passes |
|---|---|---|---|
| R0 (baseline) | 0 | n/a | Per-project isolation never tripped throttling — already known. |
| R1 | 1 | 0 | Same-project without jitter is safe → drop the sleep. |
| R2 | 1 | 1 | Confirms the current behaviour still works. |

Each run is repeated **twice** (back-to-back, then ~10 min later) to filter transient flakes from systemic throttling.

**Decision rule:**

- If R1 succeeds in **2/2 immediate runs and 2/2 spaced runs**, drop the jitter. Commit #5 becomes `refactor(image): drop unconditional jitter from --same-project (live-verified safe)`, referencing the evidence file.
- If R1 fails **any time** with HTTP 429 / 403 / a Flow-side throttle signal / overlay block, keep the jitter and land it as `docs(image): document anti-detection jitter rationale on --same-project` with a docstring + comment citing the failure case.
- If R1 is *flaky* (1/2 or 2/3 success), keep the jitter and file a follow-up issue to make it configurable — do NOT make it configurable in this PR.

**Evidence captured to `docs/LIVE_VERIFICATION_image_batch.md`:**

For every run: timestamp, profile, manifest, env-var matrix, exit code, image file paths + sizes, observed listener events, any HTTP error captured by `observability`, and a one-line verdict.

## 11. Risk register

| Risk | Likelihood | Mitigation |
|---|---|---|
| Live e2e exhausts Flow credits during the jitter matrix | Medium | Use the 3-prompt manifest only. Total spend ≈ 3 images × 3 runs = 9 generations per matrix sweep. Cap at one matrix sweep + one re-run. |
| Tree-replay split (§6.A) accidentally drops a hunk | Low | After staging, diff `feature/multi-image-prompt..origin/claude/plan-next-issue-Stegy` for `src/` and `tests/` — must be empty. |
| Flow UI changes between R1 and R2 cause false positives | Low | Run R1 and R2 within the same session, same profile. Record `git rev` of `playwright` and `chromium` versions in the evidence file. |
| Splitting commits regresses test coverage on commit #1 | Medium | Run scoped pytest after each commit, not just at the end. CI catches it too. |
| New PR misses the v0.7.x release window | Low | Targets `develop`. No release coupling in this PR. |
| Removing the dead `seed`/`batch_id` shim breaks a downstream transport not in the diff | Low | Grep `seed=` and `batch_id=` call sites across `src/gflow_cli/api/transports/` before deletion; verify only the UI transport and the to-be-removed `_drive_image_generation` reference them. |

## 12. Decision log

- **D1.** Use Strategy A (close + reopen). Rationale: only path that satisfies branch-naming convention without raw API gymnastics.
- **D2.** Atomic commit split into 5 commits. Rationale: CLAUDE.md "small, atomic commits"; lets the bugfix be cherry-picked into a release branch independently of the feature.
- **D3.** Jitter decision deferred to evidence. Rationale: project mandate to verify systematically, not guess.
- **D4.** Drop dead `seed`/`batch_id` shim in commit #1, not as a separate commit. Rationale: it's part of the same refactor that introduces `_drive_images_generation`; splitting it further is over-engineering.
- **D5.** Sample manifests committed as fixtures (not generated in-test). Rationale: doubles as user-facing copy-paste examples; the live e2e becomes hermetic.
- **D6.** Use Mechanism 6.A (tree-replay + staged commits), not interactive rebase. Rationale: CLAUDE.md forbids `git rebase -i` in the agent loop.
